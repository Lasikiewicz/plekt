# Test paid Plekt hosting without rewriting

Offer Plekt as a capped, individually isolated managed service only after clearing third-party API rights and reviewing hosted security. Test **£5 per month for founding customers and £7 regular** as hypotheses, not validated willingness-to-pay or a commitment. Run Plekt in a separate container with its own SQLite database, credentials and local persistent volume for each customer on a managed-by-us VPS; do not build shared multi-tenancy. Plekt would store watch-state metadata, configuration and possibly cached metadata/artwork, but **not host, stream or back up customers’ film or television media files**. The first pilot should accept only customers whose media server can send events to a public hosted HTTPS endpoint and whose outbound server connectivity works; a service on a home LAN is generally unreachable from a cloud VPS without networking changes or a connector. Before any public pilot, complete an internet-facing SSRF and authentication/key-recovery review and obtain clearance for commercial use of the metadata and artwork APIs the hosted build enables. If those gates fail or low-cost support is uneconomic, sell setup and maintenance help for customer-owned VPS installations instead.

## Per-customer instances fit Plekt better than shared accounts

Plekt is a long-running Node application with an in-process scheduler and local SQLite/data directory, and its authentication model is a single local administrator rather than a multi-user tenant system. The practical pilot therefore wraps **one unchanged application instance per customer**: separate container, database, configuration, encryption key, webhook secret, hostname and persistent local SSD-backed volume. A small management layer can provision and monitor instances, but application data and schedulers should remain separated. Do not place SQLite on network storage or let one customer’s container address another customer’s files or credentials. The existing container model and local storage fit a VPS, but provisioning, resource quotas, tenant deletion, billing, monitoring and support-access controls are new operator capabilities rather than ready-made SaaS features ([Plekt architecture](https://github.com/plekt/plekt/blob/develop/docs/architecture.md), [authentication](https://github.com/plekt/plekt/blob/develop/docs/auth.md), [Docker setup](https://github.com/plekt/plekt/blob/develop/docker-compose.yml)).

The customer promise should be specific: Plekt runs and maintains the sync application, stores watch history and configuration needed for it, and may cache metadata/artwork according to upstream terms. It does not store or transmit media files. State plainly that the customer’s media server, Plex/Emby/Jellyfin account, internet connection and upstream providers remain dependencies; uptime and successful sync cannot be guaranteed through their outages. Offer one service tier with one user-owned instance, defined storage/fair-use limits, stated backup retention, a support boundary and an export/deletion path. Keep support access consent-based, limited and logged. Initial onboarding can be manual; avoid building elaborate self-service signup until the pilot proves demand.

There are two feasible network patterns, and they serve different customers. A media server that can make outbound internet requests can usually send a webhook to Plekt’s public HTTPS URL; that is a simpler first pilot than asking the customer to expose their home server publicly. But Plekt also needs to contact configured media servers for some integrations and operations. A cloud instance normally cannot reach a customer’s private 192.168/10/172 LAN address. Publicly reachable HTTPS targets, a customer-managed VPN/tunnel, or deliberate port forwarding may work, but the latter two create configuration and support burden. Measure this compatibility before promising broad support. A customer-side outbound connector could later reach LAN services and relay events/commands to the hosted instance; it would need enrollment, revocation, tenant-bound credentials, replay protection and a narrow command protocol. A Docker connector still asks the customer to install, configure and maintain software, so it does not remove onboarding friction. Use it only if measured demand is being lost specifically because cloud-to-LAN connections fail. Plekt’s webhook setup and its requirement that the app host reach the media server are documented in [webhook guidance](https://github.com/plekt/plekt/blob/develop/docs/webhooks.md) and [Plex setup](https://github.com/plekt/plekt/blob/develop/docs/plex.md).

## Rights and hosted security are gates before accepting customers

AGPL-3.0 does not itself prohibit charging for hosting. If the operator modifies the program, AGPL §13 requires a prominent, no-charge offer of the running version’s Corresponding Source to users interacting with it remotely. Confirm the actual build, notices and source-link design with counsel; licensing the Plekt software does not grant rights to use or cache third-party data and imagery ([GNU AGPL v3 §13](https://www.gnu.org/licenses/agpl-3.0.html)).

Treat each enabled provider integration as its own rights question. TMDB’s FAQ says a project whose primary purpose is revenue for its owner is commercial and directs commercial API/data/image use to a separate license; that is a clear clearance gate for a paid hosted app, even if each user supplies their own API key ([TMDB FAQ](https://developer.themoviedb.org/docs/faq)). BYO keys can help separate usage and billing, but **are not a loophole** around terms governing the commercial application or display of data. TheTVDB, Fanart, OMDb and Plex also need review against the actual hosted service, features, caching and branding. TheTVDB publishes commercial licensing information, while its general terms distinguish API data from rights to images; ask for written clarification where the public terms do not settle this deployment. Disable optional integrations whose commercial rights are not cleared. Do not assume every provider must issue written approval regardless of its terms: use the published license where it clearly authorizes the intended use, and seek provider confirmation or legal advice where terms are ambiguous or a separate commercial grant is required. Trakt’s API policy appears comparatively compatible with syncing a user’s activity to that user’s account, subject to its restrictions, but confirm the current policy and use per-user authorization ([TheTVDB licensing](https://thetvdb.com/api-information), [TheTVDB terms](https://thetvdb.com/tos), [Fanart API](https://api.fanart.tv/), [OMDb terms](https://www.omdbapi.com/legal.htm), [Trakt API policy](https://developer.trakt.tv/docs/api-use-policy)).

A hosted Plekt instance accepts customer-configured server URLs and handles valuable credentials and watch history. Existing self-hosted code deliberately permits private/LAN destinations for media-server connectivity; in a public service that can become a server-side request forgery path into internal services, cloud metadata or another customer’s network. Before pilot, an independent security review must examine URL parsing, DNS resolution/rebinding, IPv4 and IPv6 ranges, redirects, authentication/session boundaries, webhook secrets, rate limits, tenant egress isolation and host control-plane exposure. Review authentication and credential/key recovery together: encrypted provider tokens depend on a separate credential key, so backups and restore must preserve or deliberately rotate that key without exposing it. Require HTTPS, unique tenant secrets, least privilege, encrypted off-host backups, a tested restore and deletion path, log redaction, alerting and an incident process. Resolve all critical/high findings before inviting paying users; any unresolved high-severity hosted boundary issue is a no-go ([Plekt outbound request validation](https://github.com/plekt/plekt/blob/develop/server/src/utils/outbound.js), [security checklist](https://github.com/plekt/plekt/blob/develop/docs/security-checklist.md), [credential handling](https://github.com/plekt/plekt/blob/develop/docs/auth.md)).

Watch history, identifiers and access tokens can relate to identifiable people. Before payment, map what is collected, purposes, processors and backups; determine controller/processor roles from actual practice; publish privacy and service terms, retention and deletion rules, support scope and cancellation route; assess ICO fee obligations and obtain UK tax advice on VAT and customer geography. The initial assumption should be UK customers only, not a conclusion that cross-border sales are simple. The ICO explains transparency and breach duties, and GOV.UK lists the current UK VAT registration threshold; applicability and VAT treatment for this specific managed service need professional review ([ICO right to be informed](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/right-to-be-informed/), [ICO data breach guide](https://ico.org.uk/for-organisations/report-a-breach/personal-data-breach/personal-data-breaches-a-guide/), [GOV.UK VAT threshold](https://www.gov.uk/how-vat-works/vat-thresholds)). GOV.UK published subscription-contract guidance on 19 October 2026; confirm commencement, applicability and cancellation/reminder requirements before taking subscriptions ([GOV.UK subscription contracts](https://www.gov.uk/government/publications/subscription-contracts)).

## Price is plausible only with low support and controlled scope

For procurement, compare Hetzner for low compute cost, DigitalOcean for a straightforward VPS alternative, and Render for reduced server administration. Published examples checked during research include Hetzner CX23 at €5.49/month excluding VAT and separate IPv4, and DigitalOcean Basic at $12/month for 2 GiB RAM. These are entry-level price references, not recommended production sizing. Render charges compute per service plus persistent disk ($0.25/GB-month), making one service per customer less attractive at a £5 subscription. Start with a VPS we administer, local SSD storage and off-host backups; select its size only after measuring representative instances ([Hetzner pricing update](https://docs.hetzner.com/general/infrastructure-and-availability/price-adjustment/), [DigitalOcean pricing](https://www.digitalocean.com/pricing/droplets), [Render pricing](https://render.com/pricing)).

Test £5/month for a founding cohort and £7/month as the regular price after the pilot. They are hypotheses to validate with actual payment intent and churn, not a market benchmark. At Stripe’s listed standard UK card rate of **1.5% + 20p**, one successful monthly payment nets roughly £4.73 from £5 or £6.70 from £7 before infrastructure, refunds, tax or support. Stripe Billing’s pay-as-you-go subscription charge is separately listed as **0.7% of Billing volume**; if used, include that in addition to card processing. Thus monthly £5 and £7 subscriptions yield roughly £4.70 and £6.67 after both listed fees, before any other costs. Confirm the pricing at launch and distinguish recurring Billing charges from card-only arithmetic ([Stripe UK pricing](https://stripe.com/gb/pricing)).

The following planning example assumes a **£60/month fixed operator budget**, not a supplier quote: VPS capacity and IP, off-host backups, monitoring, domain allocation, and a modest allowance for admin tools. Actual capacity and infrastructure price must be measured and provider quotes checked. It excludes variable customer support, VAT/tax, insurance, legal/accounting, refunds, payment disputes and setup effort. After card-only fees, 10 customers at £5 leave about £47/month, below this fixed budget; at £7 they leave about £67, only £7 before support. At 25 customers, £5 leaves about £118 and £7 about £167, or roughly £58/£107 after the assumed fixed budget. At 50 customers, £5 leaves about £236 and £7 about £335, or roughly £176/£275 after fixed budget. If Stripe Billing pay-as-you-go is used, subtract approximately another 70p per £100 billed: about 35p/49p at 10 customers, 88p/£1.23 at 25, and £1.75/£2.45 at 50 on the £5/£7 plans. These are gross contribution illustrations, not profit. At an assumed operator time value of £20/hour, just 10 support minutes per customer costs £3.33 per month, which erodes most of £5’s card-only proceeds. Keep included support tightly bounded and track minutes; setup labor should be priced separately or handled in a paid setup-only alternative.

One practical fallback is a **setup-and-maintenance service for a customer-owned VPS**: charge for installation, HTTPS, updates and optional support while the customer pays the cloud provider and holds their data. This avoids central customer-data operations and may reach users who want help self-hosting, though setup burden remains and licensing/API questions still apply if the commercial service or bundled software enables paid metadata use. If demand is strong but many homes are unreachable, test a limited connector pilot after the public-target pilot; do not build it in advance of evidence.

## Stage the work against measured go/no-go criteria

First, validate demand and topology without taking payment: interview 10–20 prospective users, record their media-server type, whether webhooks can reach a public HTTPS endpoint, whether the hosted app can reach their server, current setup pain and stated price preference. Offer a concierge configuration test using dummy/non-sensitive data where possible. Proceed only if at least five qualified households can complete the target network pattern and at least five independently indicate credible intent to pay at £5–£7; treat these as proposed screening thresholds, not market research proof.

Second, close legal, rights and security gates: inventory every provider feature and asset; clear commercial API and artwork use or disable the affected feature; review AGPL source obligations; complete the hosted SSRF/authentication/key-recovery audit; and prepare privacy, service, cancellation, export and deletion terms. Any unresolved rights question for a launch-critical feature, any critical/high security finding, or inability to restore/deprovision a tenant safely means no paid pilot. Third, run a capped 5–10 household paid pilot for a measured period, with one instance per customer. Require 100% pass on tenant-boundary checks, successful export/deletion and restore drills, no cross-customer access, and at least 99% of expected webhooks received where customer connectivity is available. Track setup completion, sync failures, uptime, storage/RAM, backup success, support minutes, refunds, payment failures and churn. Continue only if at least 80% onboard without bespoke network intervention, average ongoing support falls below five minutes/customer/month after onboarding, restore meets a published target, and recurring contribution after fees, variable infrastructure and support is positive at the tested regular price.

At 25 customers, automate provisioning and routine alerts only if the cohort is stable and support is predictable. At 50, decide whether to add a second host/region or connector based on observed capacity and failed conversions, not forecast demand. Publish no service dates or availability guarantees until recovery, monitoring and support response are proven. No customer count is currently demonstrated as safe per VPS; size the host from measured peak memory, disk growth, scheduler load, egress and restore time rather than dividing raw machine capacity by a guess.

## Conclusion

The feasible first product is a small managed service for technically compatible users, with instance isolation doing the work that a multi-tenant rewrite would otherwise require. Its viability depends less on the price of a small VPS than on API permissions, network compatibility and human support. The sensible next commitment is research and gated pilot preparation—not a launch promise: if rights or security fail, customer-owned hosting support preserves a useful paid offer without pretending those problems have disappeared.

### Remaining unknowns

No demand, conversion, churn, per-tenant load, support rate, backup cost, production capacity, provider clearance or legal review has been measured. Confirm regional hosting choice, billing and VAT treatment, data roles, API/image rights, failure recovery targets, backup retention, acceptable-use scope, and support terms before selling. Prices and policies change; recheck provider pages immediately before procurement and payment setup.
